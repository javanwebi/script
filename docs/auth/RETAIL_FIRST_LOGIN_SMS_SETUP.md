# Retail first-login and Supabase SMS verification

## What is implemented

The existing /onboarding page is shown **only to a retail customer** when their
server-backed `onboardingCompleted` preference is not `true`.
Step 1 saves one or more favorite brand IDs. Step 2 saves the business type and
the completed flag. Subsequent logins go directly to /consumer-dashboard.
This is driven by the authenticated profile, not browser local storage.
Factory/dealer/admin portals do not use the retail questionnaire.

The login and registration pages already contain password and SMS paths. For
production, phone codes are issued and verified by **Supabase Auth** only.
No code is created by the frontend or embedded in any HTML.

## Secure SMS delivery

The backend implements the Supabase **Send SMS HTTP Auth Hook** at
`POST /api/hooks/send-sms`. This endpoint requires a valid Standard Webhooks
HMAC signature with at most five minutes of timestamp skew, a server-side hook
secret, and a configured SMS provider. It accepts `user.phone` and `sms.otp`
from the signed Supabase event. The backend sends the code to either:
- `SMS_PROVIDER=kavenegar` (default): Kavenegar Verify/Lookup; requires a
  *previously approved* verify template name
- `SMS_PROVIDER=smsir`: SMS.ir Verify; requires the approved numeric
  template ID and parameter name used by the template

Never put a key or the hook secret in GitHub, a public `VITE_*` variable,
URL query strings, frontend forms or logs.

## VPS configuration

Create `/opt/sanatpish/.env.sms` as a root-owned, mode-0600 file.
The application reads this Git-ignored file at startup.
Use the environment variables for **only your real provider**:

```dotenv
# Choose "kavenegar" or "smsir"
SMS_PROVIDER=kavenegar
KAVENEGAR_API_KEY=YOUR_SECRET_KEY
KAVENEGAR_VERIFY_TEMPLATE=YOUR_APPROVED_TEMPLATE

# Alternative when SMS_PROVIDER=smsir
# SMSIR_API_KEY=YOUR_SECRET_KEY
# SMSIR_TEMPLATE_ID=YOUR_APPROVED_NUMERIC_TEMPLATE
# SMSIR_CODE_PARAMETER=Code

# Generated by Supabase Dashboard Authentication > Hooks > Send SMS
SUPABASE_SEND_SMS_HOOK_SECRET=v1,whsec_YOUR_HOOK_SECRET

# Leave false until provider, HTTPS hook and real SMS test are ready
SUPABASE_SMS_READY=false
```

In Supabase Dashboard:
1. Authentication > Providers > Phone: enable phone OTP, disable automatic
   phone confirmation (verification must be required).
2. Authentication > Hooks > Send SMS: choose **HTTP**, URL
   `https://YOUR_HTTPS_DOMAIN/api/hooks/send-sms` (publicly accessible HTTPS).
   Use the matching hook secret in the private .env.sms file. The IP-only
   HTTP URL is **not** appropriate for managed Supabase Auth.
3. Set the provider-specific API key and approved template in .env.sms.
   Verify outbound connectivity from the VPS to the provider API.
4. Set `SUPABASE_SMS_READY=true` only after the hook and provider are
   configured. Restart the existing application with the normal guarded
   deployment workflow. Do not restart Supabase/Postgres or FORZA voice.
5. Test on an **authorized test mobile**: request an OTP via /register,
   verify in Supabase Auth, create credentials, complete both onboarding
   questions, log out, then log in via SMS. Confirm onboarding does not recur.
   Test an unknown phone via /login: it must not create a new identity.

Note: if your Supabase Auth instance is self-hosted, the hook is configured
through `GOTRUE_HOOK_SEND_SMS_ENABLED`, `GOTRUE_HOOK_SEND_SMS_URI` and
`GOTRUE_HOOK_SEND_SMS_SECRETS` on the Auth container; for managed Supabase,
configure it through Authentication > Hooks. Do not independently send
an application-generated code in addition to the Supabase code.

## Smoke checks

Unauthenticated webhook calls must fail without dispatching messages:

```bash
curl -i -X POST http://127.0.0.1:3001/api/hooks/send-sms \
  -H 'Content-Type: application/json' --data '{}'
```

Expect 401 when fully configured (or 503 while SMS is not enabled).
The application health endpoint alone does **not** prove SMS delivery.
Never print provider responses, signature secrets, OTP codes or credentials.
