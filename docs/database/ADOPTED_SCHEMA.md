# ساختار واقعی صنعت پیش — ۲۰ اکتبر ۲۰۲۶

مبنای این بسته، SQL ارسالی مالک و ساختار بررسی‌شده مستقیم در پروژه `sanatpish` است: ۴۹ جدول public، شامل `user_profiles`، `catalog_families`، `catalog_variants` و `variant_commercial_specs`.

در زمان بررسی، ۱٬۳۸۳ خانواده، ۱۰٬۴۳۵ کد کالا و ردیف تجاری و ۸۶۹ رکورد ممیزی تصویر وجود داشت. جدول‌های پروفایل و سفارش خالی بودند. این داده‌ها وارد شده‌اند؛ این بسته دوباره آن‌ها را import نمی‌کند.

## فایل مناسب برای شما

- دیتابیس فعلی: `docs/database/sql/Upgrade_Existing_Database.sql`.
- فقط یک Supabase کاملاً تازه: `docs/database/sql/Full_Fresh_Database.sql`.
- `Manifest.json`: هش SHA256 فایل‌های Migration و فایل مبنا.

فایل کامل را روی دیتابیس فعلی اجرا نکنید. هر دو فایل در یک transaction اجرا می‌شوند. نسخه ارتقا عمداً تکرار اجرا را رد می‌کند؛ پس از اجرا از Migrationهای نسخه‌بندی‌شده بعدی استفاده کنید.

**SQLهای اولیه در مسیر ریشه `supabase/migrations` و importer قدیمی، برای یک ساختار آزمایشی متفاوت با نام‌های `profiles` / `product_families` هستند. روی ساختار واقعی شما اجرا نشوند.** فرمان قدیمی مهاجرت برای جلوگیری از این اشتباه روی دیتابیس adopted متوقف می‌شود. آداپتور ساختار واقعی با `DATABASE_SCHEMA=adopted` اضافه شده است. وضعیت انتقال پروژه جدید و محدودیت‌های اتصال زنده در [SANATPISHATLAS.md](SANATPISHATLAS.md) ثبت شده است. تا تطبیق داده‌های volume سایت زنده و تست ورود و پرداخت، `DATA_BACKEND` روی سرویس اصلی تغییر نکند.

## تغییرات امنیتی سازگار

- نقش از `raw_user_meta_data` گرفته نمی‌شود؛ ثبت‌نام عادی `client` است.
- تطبیق CRM فقط با شماره یا ایمیل تأییدشده Auth انجام می‌شود؛ تطبیق مبهم خودکار پذیرفته نمی‌شود.
- نقش، گرید، اعتبار و مانده‌های مالی با UPDATE مستقیم مشتری قابل تغییر نیستند.
- قیمت‌های داخلی عمده/نماینده و اطلاعات گرید و CRM از SELECT عمومی مشتری حذف می‌شوند.
- RPC کاتالوگ به مشتری فقط قیمت خودش را برمی‌گرداند و دسترسی موجودی را جداگانه بررسی می‌کند.
- بنر و اطلاعیه شخصی براساس مالک و پنل هدف خوانده می‌شوند.
- کاربر مهمان نمی‌تواند سفارش یا استعلام با هویت دلخواه درج کند؛ مسیر BFF باید ورود و هویت را بررسی کند.
- `warehouse_operator` و `sales_manager` مدیر کل محسوب نمی‌شوند. تغییر نقش و عملیات مدیریتی باید از backend مورداعتماد با بررسی نقش مناسب انجام شود.
- RLS جای مجوز ستونی را نمی‌گیرد. بخش پروفایل frontend باید ستون‌های مجاز را مشخص کند و از `select *` برای پروفایل، CRM و نمایندگان استفاده نکند.

## جدول‌ها و عملیات تکمیلی

۱۴ جدول public برای دفتر مالی، حساب افتتاحیه تطبیق‌شده، گردش و رزرو موجودی/اعتبار، تلاش پرداخت و برگشت، ارسال سفارش، تاریخچه وضعیت، آدرس‌ها، مستندات، پیام تیکت، مصرف جوایز و کلید درخواست سفارش اضافه می‌شوند. صف اعلان و ثبت نسخه schema در `app_private` قرار می‌گیرند.

توابع داخلی شامل ثبت تکرارناپذیر گردش مالی، اصلاح موجودی، رزرو/مصرف/آزادسازی موجودی، رزرو/تأیید اعتبار، ثبت نتیجه پرداخت و برگشت وجه پس از تأیید واقعی provider و دریافت نوبتی اعلان‌ها هستند. این توابع `SECURITY INVOKER` هستند و مرورگر اجازه اجرای آن‌ها را ندارد. آن‌ها جای فراخوانی واقعی درگاه یا پیامک را نمی‌گیرند. اجرای `record_verified_payment` فقط بعد از تأیید server-to-server درگاه و تطبیق مبلغ و واحد پول مجاز است؛ صرف تغییر UI یا callback مرورگر کافی نیست.

حساب افتتاحیه باید از منبع واقعی تطبیق شود. هیچ مانده، پرداخت، پیامک تحویل‌شده، کد کالا یا امتیاز ساختگی ایجاد نمی‌شود. واحد ثبت‌شده فعلی `IRR` است؛ مبالغ بدون تبدیل حفظ می‌شوند. اگر مقادیر منبع در واقع تومان بوده‌اند، ابتدا تطبیق واحد انجام دهید؛ این بسته مبلغ را ده‌برابر/یک‌دهم نمی‌کند.

Storage شامل `catalogue` عمومی و `customer-documents` خصوصی است. مسیر مدارک خصوصی باید با UUID کاربر Auth آغاز شود. مشتری اجازه جایگزینی/حذف مدارک ندارد. فایل‌های قدیمی از دیسک یا GitHub خودکار به Storage کپی نشده‌اند.

## تست و وضعیت اجرا

۱۰ تست دیتابیس (شامل ۷ تست ساختار adopted) و ۲۶ تست قبلی پنل پاس شده‌اند؛ بررسی TypeScript و build نیز موفق بوده‌اند. ۷ تست روی PostgreSQL ایزوله PGlite، بر اساس همان schema ارسالی، ثبت‌نام، تأیید CRM، مجوزهای ستونی، قیمت، محتوای تکی، دفتر مالی، رزرو موجودی و اعتبار، پرداخت، Storage و بازیابی پشتیبان مجوزها را بررسی می‌کنند. Auth و Storage در این تست‌ها فقط کاتالوگ SQL آزمایشی دارند؛ سرویس HTTP/OTP و درگاه واقعی آزمایش نشده‌اند. نوع/ایندکس/RPC برداری از fixture حذف شده‌اند؛ تست برداری با سرویس واقعی جداست و این بخش تغییری نمی‌کند.

از توابع، Policyها و grantهای فعلی و پروفایل/CRM پیش از تغییر، پشتیبان محدود به محدوده اصلاحات گرفته شد. بازیابی آن در محیط آزمایشی تست شد. این پشتیبان جای `pg_dump` کامل و نسخه پشتیبان Storage را برای cutover کامل نمی‌گیرد.

**اجرای Migration روی پروژه قدیمی `sanatpish` توسط بازبینی خودکار رد شد و روی آن پروژه اجرا نشد.** سپس مالک پروژه خالی جدید `sanatpishatlas` را معرفی و ایجاد ساختار و انتقال را صریحاً درخواست کرد؛ بسته اولیه و Migration اتصال runtime روی پروژه جدید اعمال شدند. دیتابیس قدیمی دست‌نخورده است. برای تغییرات بعدی Production همچنان بررسی، پشتیبان و تأیید صریح مالک لازم است.

## توسعه بعدی

قبل از هر تغییر، schema واقعی را بخوانید. برای ساختار جدید Migration نسخه‌دار بسازید؛ فایل اعمال‌شده تغییر نکند. API، TypeScript، validation و مجوزها با schema هماهنگ شوند. `supabase/adopted/baseline/user_supplied_master.sql` صرفاً سابقه مبناست و مجدداً روی Production اجرا نمی‌شود.
